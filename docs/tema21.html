Dónde se escribe y se ejecuta un programa, qué ocurre cuando falla y cómo se demuestra que una corrección funciona.

Antes de empezar: tu programa se ejecuta sin errores pero da un resultado equivocado. ¿Por dónde empiezas?
Al terminar serás capaz de…
  • identificar los componentes de un entorno de programación
  • comparar Jupyter Notebook y Thonny y elegir según la tarea
  • explicar qué ocurre al ejecutar un programa compilado y uno interpretado
  • distinguir errores de sintaxis, de ejecución y de lógica
  • leer una traza de error y localizar la línea culpable
  • depurar paso a paso con puntos de interrupción e inspección de variables
  • diseñar casos de prueba normales, límite y no válidos

1. Qué compone un entorno de programación

Un entorno de programación reúne las herramientas necesarias para escribir, ejecutar y corregir programas. Sus componentes son siempre los mismos, aunque cambie el aspecto:

ComponentePara qué sirve
EditorEscribir el código, con coloreado de sintaxis, sangría automática y avisos de error mientras escribes.
Motor de ejecuciónEjecutar el programa: el intérprete de Python.
ConsolaVer la salida, introducir datos y probar instrucciones sueltas.
DepuradorEjecutar paso a paso, detener el programa e inspeccionar el valor de las variables.
Gestión de bibliotecasInstalar y actualizar los módulos que el programa necesita.

Cuando esos componentes vienen integrados en una sola aplicación se habla de un IDE (entorno de desarrollo integrado). Thonny lo es; un Notebook cubre casi todo salvo el depurador.

2. Jupyter Notebook con Google Colab

Es el entorno principal del curso y ya lo conoces del Tema 16. Sus rasgos:

Sin instalación

Funciona en el navegador desde cualquier equipo del centro o de casa, con la misma sesión y los mismos archivos.

Texto y código juntos

El mismo documento contiene la explicación y el programa ejecutable, con el resultado bajo cada celda.

Ejecución por celdas

Se prueba un trozo pequeño sin ejecutar todo lo demás: ideal para explorar y para aprender.

Estado persistente

Las variables sobreviven entre celdas, lo que ahorra recalcular… y provoca confusiones si se ejecutan en desorden.

Sus dos limitaciones realesUn Notebook no tiene depurador paso a paso con la comodidad de un IDE, y su estado oculto permite que un documento parezca correcto cuando en realidad depende del orden en que ejecutaste las celdas. Por eso el curso usa un segundo entorno.

3. Thonny: el entorno local

Thonny es un IDE de Python pensado expresamente para quien está aprendiendo. Se instala en el equipo, trae Python incluido y su interfaz no esconde nada de lo que hace falta.

Jupyter Notebook (Colab)Thonny
Dónde se ejecutaEn un servidor remoto, desde el navegador.En tu propio equipo, sin conexión.
Unidad de trabajoCeldas dentro de un archivo .ipynb.Un programa completo en un archivo .py.
EjecuciónCelda a celda, en el orden que elijas.El archivo entero, siempre de arriba abajo.
EstadoPersiste entre celdas.Empieza limpio en cada ejecución.
DepuradorLimitado.Paso a paso, con puntos de interrupción e inspección de variables.
Mejor paraExplorar, explicar, probar ideas.Programas completos y, sobre todo, buscar errores.
Por qué dos entornos y no unoPorque resuelven problemas distintos. El Notebook es imbatible para aprender y para documentar; Thonny es imbatible para ver qué está haciendo realmente un programa. Y su ejecución siempre desde cero, en orden, elimina de raíz el problema del estado oculto: si un programa funciona en Thonny, funciona.
💡 Un archivo .py es texto plano: solo el programa, sin celdas ni resultados guardados. Es el formato con el que se distribuye el software real, y el que abrirá cualquier otro editor. Un .ipynb, en cambio, es un documento con el código, el texto y las salidas almacenadas.

4. Compilar frente a interpretar

En el Tema 9 viste las tres estrategias de traducción. Ahora que programas, conviene concretar qué ocurre exactamente al ejecutar tu código.

Lenguaje compilado (C)Python
Antes de ejecutarEl compilador traduce todo el programa a código máquina y produce un ejecutable.No hay paso previo: se lanza y se ejecuta.
Errores de sintaxisSe detectan todos al compilar, antes de ejecutar nada.Se detectan al analizar el archivo, también antes de ejecutar.
Al ejecutarEl procesador ejecuta directamente el código máquina.El intérprete lee y ejecuta las instrucciones.
Se distribuyeUn ejecutable, sin código fuente.El código fuente; hace falta tener Python instalado.
💡 En realidad Python hace un paso intermedio: antes de ejecutar, traduce el código a una representación interna más eficiente y la guarda para no repetir el trabajo. Es lo que hay dentro de esas carpetas __pycache__ que aparecen solas junto a tus archivos. La frontera entre compilado e interpretado, como se decía en el Tema 9, es más borrosa de lo que parece.

5. Los tres tipos de error

TipoCuándo apareceCómo se manifiestaDificultad
SintaxisAntes de ejecutar nada.SyntaxError con el número de línea.Baja: el intérprete te lleva al sitio.
EjecuciónDurante la ejecución.El programa se detiene con una excepción y una traza.Media: sabes dónde y qué pasó.
LógicaNunca: el programa termina «bien».El resultado es incorrecto, y nada avisa.Alta: hay que descubrirlo.

5.2. Errores de ejecución: las excepciones

Una excepción es un error que ocurre mientras el programa se ejecuta y que lo detiene. Los que más te encontrarás:

ExcepciónQué significaCausa típica
NameErrorSe usa un nombre que no existe.Variable mal escrita o aún no creada.
TypeErrorOperación imposible entre esos tipos.Sumar un texto y un número.
ValueErrorEl tipo es correcto, el valor no.int("hola").
IndexErrorÍndice fuera de la lista.Acceder a lista[5] en una lista de 5.
ZeroDivisionErrorDivisión entre cero.Calcular la media de una lista vacía.
IndentationErrorSangría incoherente.Mezclar espacios y tabuladores.
💡 Python permite capturar las excepciones para que el programa no se detenga y pueda reaccionar. Es contenido de Ciencias de la Computación II. En 1.º basta con saber reconocerlas, entender qué las provoca y evitarlas comprobando los datos antes, como con el isdigit() del Tema 19.

5.3. Errores de lógica

def precio_con_descuento(precio, porcentaje):
    # Falla lógicamente: suma el descuento en vez de restarlo.
    return precio + precio * porcentaje / 100

print(precio_con_descuento(80, 25))   # 100.0; se esperaba 60.0
100.0
El error de lógica es el peligrosoNo hay mensaje, no hay línea señalada, no hay aviso. El programa hace exactamente lo que escribiste, y lo que escribiste no era lo que querías. Solo se detecta comprobando los resultados contra lo que esperabas, y por eso las pruebas no son un adorno: son la única herramienta que existe contra esta clase de error.

6. Leer un mensaje de error y su traza

Cuando salta una excepción, Python imprime una traza (traceback) con toda la información necesaria. Mucha gente se asusta y no la lee; es un error, porque casi siempre dice exactamente qué pasa.

Traceback (most recent call last):
  File "notas.py", line 12, in <module>
    print(calcular_media(notas))
  File "notas.py", line 3, in calcular_media
    return sum(numeros) / len(numeros)
ZeroDivisionError: division by zero
ParteQué te dice
Traceback (most recent call last)Empieza la traza. Lo más reciente está al final: se lee de abajo arriba.
La última líneaEl tipo de excepción y su explicación. Es lo primero que hay que leer.
El bloque inmediatamente anteriorEl archivo, la línea y el código exactos donde ocurrió.
Los bloques de arribaEl camino de llamadas que llevó hasta allí: quién llamó a quién.
Cómo se lee una trazaDe abajo arriba y en dos pasos. Primero, la última línea: dice qué ha pasado —una división por cero—. Después, el bloque de encima: dice dónde —línea 3, dentro de calcular_media—. Con esas dos cosas ya sabes que len(numeros) valía cero, es decir, que le llegó una lista vacía. La traza no ha señalado el error: ha señalado dónde se manifestó. La causa está en quien pasó una lista vacía.
Dónde se manifiesta no es dónde está la causaEs la distinción que más tiempo ahorra al depurar. En el ejemplo, la línea 3 es correcta; el problema es que alguien llamó a la función con datos que no había previsto. Arreglar la línea 3 sin más taparía el síntoma. Es el mismo criterio del Tema 6: identificar la fase en la que falla algo no es lo mismo que identificar su causa.

7. Depuración paso a paso con Thonny

Poner print() por todas partes funciona y es legítimo, pero es lento y hay que acordarse de quitarlos. Un depurador hace lo mismo mejor: detiene el programa donde quieras y te deja mirar dentro.

HerramientaQué hace
Punto de interrupciónMarca una línea donde el programa se detendrá al llegar.
Ejecutar paso a pasoAvanza una instrucción cada vez, para ver el recorrido real.
Entrar en la funciónEn lugar de saltarla, sigue la ejecución dentro de ella.
Inspector de variablesMuestra el valor de cada variable en ese instante, y cómo cambia.
ContinuarReanuda hasta el siguiente punto de interrupción.
Por qué Thonny y no otroThonny está diseñado para enseñar, y su depurador hace algo que los profesionales no: muestra cómo se evalúa una expresión por dentro, sustituyendo paso a paso cada parte por su valor. Ver cómo 2 + 3 * 4 se convierte primero en 2 + 12 y luego en 14 explica la precedencia del Tema 17 mejor que cualquier tabla.
💡 El depurador sirve para dos cosas distintas, y la segunda es la más valiosa: encontrar errores, sí, pero también entender un programa que no escribiste tú. Recorrer paso a paso un código ajeno viendo cambiar las variables es la forma más rápida de comprender qué hace.

8. Probar: casos normales, límite y no válidos

Probar es ejecutar el programa con datos elegidos a propósito y comparar el resultado con el esperado. Y para elegirlos bien hay tres categorías:

Casos normales

Datos típicos, los que el programa recibirá el 99 % de las veces. Comprueban que hace lo básico.

Casos límite

Los bordes: cero, uno, vacío, el máximo, el mínimo, el valor justo de la frontera. Aquí falla casi todo.

Casos no válidos

Lo que no debería llegar: texto donde va un número, negativos, una lista vacía. Comprueban qué pasa cuando algo va mal.

8.1. Una tabla de casos de prueba

Para la función calificar(nota) del Tema 20, que devuelve «Aprobado» si la nota llega a 5:

EntradaTipo de casoResultado esperado
7Normal, aprobado"Aprobado"
3Normal, suspenso"Suspenso"
5Límite exacto"Aprobado"
4.99Justo por debajo"Suspenso"
0 y 10Extremos del rango"Suspenso" y "Aprobado"
-3No válidoDecidir y documentar qué debe pasar.
El caso que nunca se pruebaLos alumnos prueban el 7 y el 3, y dan el programa por bueno. Los errores viven en el 5 exacto: es donde se decide si la condición era >= o >, y ese detalle no se manifiesta con ningún otro valor. Cuando definas un caso de prueba, empieza siempre por la frontera.

8.2. Comprobar automáticamente con assert

Escribir las comprobaciones en el propio programa permite repetirlas en un segundo cada vez que cambies algo:

def calificar(nota):
    """Devuelve 'Aprobado' si la nota alcanza el 5, y 'Suspenso' si no."""
    return "Aprobado" if nota >= 5 else "Suspenso"

assert calificar(7) == "Aprobado"
assert calificar(3) == "Suspenso"
assert calificar(5) == "Aprobado"      # el caso frontera
assert calificar(4.99) == "Suspenso"
print("Todas las comprobaciones han pasado.")
Todas las comprobaciones han pasado.

assert no hace nada si la condición se cumple, y detiene el programa con un AssertionError si falla. Es la forma más barata de tener pruebas: se escriben una vez y avisan solas.

💡 Esto es lo que hace tan rentable la separación del Tema 20: una función de cálculo pura se comprueba con cuatro assert; una que además pide datos por teclado, no. Separar el cálculo es lo que hace posible probar.

9. Un método completo de depuración

Aquí está la respuesta a la pregunta guía. Depurar no es mirar el código fijamente esperando la iluminación: es un procedimiento.

1 — Reproducir el fallo

Encuentra unos datos concretos con los que el error ocurra siempre. Un error que no sabes reproducir no lo puedes arreglar, y tampoco podrás comprobar si lo arreglaste.

2 — Escribir qué esperabas

Con esa entrada, qué salida debería dar y cuál da. Por escrito. Suena obvio y la mitad de las veces, al escribirlo, aparece el error.

3 — Reducir el caso

Simplifica los datos hasta el mínimo que siga fallando. Es mucho más fácil depurar con tres notas que con treinta.

4 — Localizar la zona

Divide el programa en dos y comprueba en el medio si los datos ya son incorrectos. Repite. Cada comprobación descarta la mitad del código, igual que la búsqueda del Tema 1.

5 — Observar los valores reales

Con el depurador o con print(), mira qué valen las variables en ese punto. Casi siempre alguna no vale lo que dabas por hecho.

6 — Formular una hipótesis y comprobarla

«Creo que falla porque la lista llega vacía». Compruébala antes de tocar nada: si no era eso, habrás aprendido algo igualmente.

7 — Corregir una sola cosa

Un cambio cada vez. Si cambias tres y funciona, no sabrás cuál era, y volverá a pasarte.

8 — Volver a probar todo

El caso que fallaba y también los que ya funcionaban: una corrección puede romper otra cosa. Si tienes assert, esto cuesta un segundo.

El mismo método de todo el cursoCompara estos ocho pasos con el diagnóstico de un equipo que no arranca del Tema 6: reproducir el síntoma, reducir posibilidades con evidencias y cambiar una sola cosa cada vez. Es el mismo procedimiento, aplicado a un programa en lugar de a una placa base. Depurar no es una habilidad de programador: es el método experimental.
Dos hábitos que ahorran horasEl primero: cuando lleves veinte minutos atascado, explícale el problema en voz alta a alguien, aunque no sepa programar. Verbalizarlo obliga a ordenar lo que sabes y el error suele aparecer solo. El segundo: levántate y vuelve luego. Un error que resiste una hora de insistencia cae en dos minutos al día siguiente, y eso no es casualidad: mirar el mismo código repetidamente hace que dejes de leerlo y empieces a recordarlo.
🤔 Para pensar: con lo aprendido en todo el bloque, vuelve al programa de estadísticas del Tema 20 y prueba a llamar a calcular_media([]). Obtendrás un ZeroDivisionError. Ahora responde a tres preguntas: ¿dónde se manifiesta el error?, ¿dónde está su causa? y ¿qué debería hacer el programa en ese caso? La tercera no tiene una respuesta técnica: es una decisión de diseño, y tomarla es lo que separa un programa que funciona de uno que solo funciona a veces.

Glosario del tema

Entorno de programación
Conjunto de herramientas para escribir, ejecutar y corregir programas.
IDE
Entorno de desarrollo integrado: editor, ejecución, consola y depurador en una sola aplicación.
Thonny
IDE de Python orientado al aprendizaje, con depurador paso a paso.
Archivo .py
Programa de Python en texto plano, que se ejecuta entero y de arriba abajo.
Excepción
Error que ocurre durante la ejecución y detiene el programa.
Traza
Informe que Python imprime al producirse una excepción; se lee de abajo arriba.
Error de lógica
Fallo que no produce ningún aviso: el programa termina y el resultado es incorrecto.
Depurador
Herramienta que detiene el programa y permite inspeccionar sus variables.
Punto de interrupción
Marca en una línea donde el depurador detendrá la ejecución.
Caso de prueba
Conjunto de datos de entrada con su resultado esperado.
Caso límite
Dato situado en la frontera de lo permitido: cero, vacío, el valor exacto de corte.
assert
Instrucción que comprueba una condición y detiene el programa si no se cumple.
Reproducir
Conseguir que un error ocurra siempre con unos datos concretos.
Refactorizar
Mejorar la estructura del código sin cambiar lo que hace.

Resumen esencial

  1. Un entorno reúne editor, ejecución, consola, depurador y gestión de bibliotecas; cuando va todo junto es un IDE.
  2. El Notebook es mejor para explorar y explicar; Thonny, para ver qué hace realmente un programa y depurarlo.
  3. El estado oculto de un Notebook desaparece en Thonny, porque siempre ejecuta desde cero y en orden.
  4. Los errores de sintaxis paran antes de ejecutar; las excepciones, durante; los de lógica no paran nunca.
  5. Una traza se lee de abajo arriba: primero qué pasó, después dónde.
  6. Dónde se manifiesta un error no es dónde está su causa.
  7. Se prueba con casos normales, límite y no válidos, y los errores viven en la frontera exacta.
  8. Cuatro assert son pruebas de verdad, y solo son posibles si el cálculo está separado.
  9. Depurar es un método de ocho pasos, el mismo que diagnosticar una avería: reproducir, reducir, observar y cambiar una cosa cada vez.
